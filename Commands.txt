K8-LAB: JENKINS + MINIKUBE VM DEPLOYMENT COMMANDS
================================================

This guide deploys the microservices from VM1 (Jenkins/build VM) to VM2
(Minikube VM), then exposes them through the NGINX Ingress controller.

Assumptions
-----------
- Ubuntu VMs share a VirtualBox host-only network.
- Example VM2 IP: 192.168.56.102. Replace it with VM2's actual host-only IP.
- The code is on branch: srinath6132-minikube-microservices.
- Replace YOUR_DOCKERHUB_USER with your Docker Hub namespace.
- This lab uses an i7 dual-core, 16 GB RAM, 256 GB SSD laptop. Keep Jenkins
  to one executor. While both VMs run, use about 3-4 GB for VM1 and 5-6 GB
  for VM2, leaving at least 6 GB for Windows. These vCPUs share the laptop's
  two physical cores. Stop VM1 before enabling Prometheus/Grafana.
- Run all VM2 Minikube/kubectl/Helm commands as the same Linux account that
  Jenkins uses for SSH (shown below as "deploy"). Minikube profiles are
  user-specific. Do not use sudo with kubectl, Helm, or deployment commands.
- The repository root Jenkinsfile belongs to the legacy app. Use the
  microservice pipeline paths listed in the Jenkins section.
- The shop services, users, and carts use in-memory data. Restarts reset it.


0. UPDATE AN EXISTING CLONE TO THE LATEST BRANCH
-------------------------------------------------

If the repository is already cloned on VM1 or VM2, use its existing working
directory rather than cloning over it. Check for local edits first:

  cd ~/k8-lab
  git status --short
  git fetch origin
  git switch srinath6132-minikube-microservices
  git pull --ff-only origin srinath6132-minikube-microservices

If `git pull` reports unstaged changes, do not discard them. Inspect and
commit or safely save those edits, then retry. If `git switch` fails because
the branch is missing locally, use:

  git switch --track origin/srinath6132-minikube-microservices

Confirm the new source is present before proceeding:

  git log -1 --oneline
  test -f k8s/resource-management/shop-quota.yaml && echo "shop quota manifest found"


1. VM2: INSTALL MINIKUBE AND PREPARE THE DEPLOYMENT ACCOUNT
----------------------------------------------------------

Clone the repository and run the checked-in VM2 installer:

  sudo apt-get update
  sudo apt-get install -y git
  git clone --branch srinath6132-minikube-microservices https://github.com/srinath6132/k8-lab.git
  cd k8-lab
  chmod +x scripts/install-vm2-minikube.sh
  ./scripts/install-vm2-minikube.sh

Create a dedicated deploy account and add it to the Docker group:

  sudo adduser deploy
  sudo usermod -aG docker deploy

Log out and reconnect as deploy so the new group membership takes effect.
Start a login shell as deploy (or reconnect to VM2 as deploy). Start Minikube
as that account and enable the ingress addon:

  sudo -iu deploy
  minikube start --driver=docker --cpus=2 --memory=6144
  minikube status
  kubectl get nodes
  minikube addons enable ingress
  kubectl -n ingress-nginx get pods,svc

For the first setup, clone the repository as deploy. If its clone already
exists, skip the two clone commands and update it using section 0. Then
create the namespace/guardrails and the JWT secret required by the
auth/user/cart services:

  git clone --branch srinath6132-minikube-microservices https://github.com/srinath6132/k8-lab.git
  cd k8-lab
  kubectl apply -f k8s/namespaces/shop.yaml
  kubectl apply -f k8s/resource-management/shop-quota.yaml
  kubectl -n shop create secret generic shop-jwt --from-literal=jwt-secret="$(openssl rand -base64 48)"
  kubectl -n shop get secret shop-jwt

Keep the generated JWT secret out of source control. The Jenkins deploy
script expects the Secret name "shop-jwt" and data key "jwt-secret".
Create the JWT secret only once; if it already exists, keep the same secret
so previously issued demo tokens remain valid:

  kubectl -n shop get secret shop-jwt

If it does not exist, run the `kubectl create secret` command above. Do not
delete/recreate the namespace on routine deployments.

If the Kubernetes images are private, create a Docker Hub image pull secret
in the shop namespace. Use a Docker Hub access token, not your password:

  kubectl -n shop create secret docker-registry dockerhub-pull \
    --docker-server=https://index.docker.io/v1/ \
    --docker-username=YOUR_DOCKERHUB_USER \
    --docker-password=YOUR_DOCKERHUB_ACCESS_TOKEN \
    --docker-email=YOUR_EMAIL

Enter "dockerhub-pull" for IMAGE_PULL_SECRET_NAME in the Jenkins job.
For public images, leave IMAGE_PULL_SECRET_NAME blank and skip this step.


2. VM1: INSTALL JENKINS AND BUILD TOOLS
---------------------------------------

Clone the same branch and run the VM1 installer:

  sudo apt-get update
  sudo apt-get install -y git
  git clone --branch srinath6132-minikube-microservices https://github.com/srinath6132/k8-lab.git
  cd k8-lab
  chmod +x scripts/install-vm1-ubuntu.sh
  ./scripts/install-vm1-ubuntu.sh

Install Jenkins from its Debian repository:

  sudo install -d -m 0755 /etc/apt/keyrings
  sudo curl -fsSL -o /etc/apt/keyrings/jenkins-keyring.asc https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key
  echo "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/" | sudo tee /etc/apt/sources.list.d/jenkins.list >/dev/null
  sudo apt-get update
  sudo apt-get install -y jenkins
  sudo usermod -aG docker jenkins
  sudo systemctl enable --now jenkins
  sudo systemctl restart jenkins

Docker group membership grants root-equivalent privileges. Use this only
on a dedicated lab VM. If you also added your login account to the group,
log out and back in.

In Manage Jenkins > Nodes > Built-In Node > Configure, set the number of
executors to 1 to limit CPU and memory pressure.

Check VM1 can reach VM2 and SSH as deploy:

  ping -c 3 192.168.56.102
  ssh deploy@192.168.56.102 'minikube status && kubectl get nodes && helm version --short'


3. SET UP THE JENKINS-TO-VM2 SSH KEY
------------------------------------

On VM1, generate a dedicated key. Protect the private key:

  ssh-keygen -t ed25519 -C jenkins-vm2-deploy -f ~/.ssh/jenkins-vm2-deploy
  ssh-copy-id -i ~/.ssh/jenkins-vm2-deploy.pub deploy@192.168.56.102

In Jenkins, go to Manage Jenkins > Credentials and add:

- ID: dockerhub-creds
  Kind: Username with password
  Username: Docker Hub username
  Password: Docker Hub access token

- ID: vm2-ssh-key
  Kind: SSH Username with private key
  Username: deploy
  Private key: paste the contents of ~/.ssh/jenkins-vm2-deploy

Do not commit either credential or put it in pipeline parameters.

The pipelines use StrictHostKeyChecking=yes. Before adding VM2's host key
to Jenkins' known_hosts, verify the VM2 SSH host-key fingerprint.

On VM2:

  sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

On VM1, capture and inspect the key fingerprint; compare it with the VM2
fingerprint before trusting it:

  ssh-keyscan -t ed25519 192.168.56.102 > /tmp/vm2_known_hosts
  ssh-keygen -lf /tmp/vm2_known_hosts

After confirming the fingerprints match, install the key for Jenkins:

  sudo install -d -o jenkins -g jenkins -m 0700 /var/lib/jenkins/.ssh
  sudo sh -c 'cat /tmp/vm2_known_hosts >> /var/lib/jenkins/.ssh/known_hosts'
  sudo chown jenkins:jenkins /var/lib/jenkins/.ssh/known_hosts
  sudo chmod 0600 /var/lib/jenkins/.ssh/known_hosts
  rm -f /tmp/vm2_known_hosts


4. CREATE THE JENKINS PIPELINE
------------------------------

Install/enable these Jenkins plugins:

- Pipeline
- Git
- GitHub Branch Source (for GitHub branch discovery)
- Credentials Binding
- SSH Agent

Create a Multibranch Pipeline job for this repository. Configure GitHub
branch discovery and set the Script Path to:

  jenkins/pipelines/Jenkinsfile.orchestrator

Scan the repository branches. Build
`srinath6132-minikube-microservices`. The orchestrator's default
`DEPLOY_BRANCH` is `main`; set it to
`srinath6132-minikube-microservices` for this lab branch, or Jenkins will
successfully build but skip deployment. Deployment also requires
`DEPLOY_TO_MINIKUBE=true`.
The orchestrator pipeline tests all four services, builds/scans/pushes
their images, then uses SSH to deploy them to VM2 with Helm.

Set the pipeline parameters:

- DOCKERHUB_IMAGE_BASE = YOUR_DOCKERHUB_USER/k8-lab
- VM2_HOST = 192.168.56.102
- VM2_USER = deploy
- DEPLOY_BRANCH = srinath6132-minikube-microservices
- DEPLOY_TO_MINIKUBE = true
- IMAGE_PULL_SECRET_NAME = blank for public images, otherwise dockerhub-pull

The pipeline appends service names to DOCKERHUB_IMAGE_BASE, producing
repositories such as YOUR_DOCKERHUB_USER/k8-lab-user-service. Ensure these
repositories can be pushed to by the supplied Docker Hub credentials.

To create separate service Multibranch Pipeline jobs, use these Script
Paths (one job per service):

  jenkins/pipelines/Jenkinsfile.user-service
  jenkins/pipelines/Jenkinsfile.auth-service
  jenkins/pipelines/Jenkinsfile.product-service
  jenkins/pipelines/Jenkinsfile.cart-service

Per-service jobs default to not deploying. Enable DEPLOY_TO_MINIKUBE only
for an intentional service release. Do not use the repository-root
"Jenkinsfile" for the microservice jobs; it is for the legacy app.


5. CHECK THE RELEASE ON VM2
---------------------------

After the Jenkins orchestrator build succeeds, run on VM2 as deploy:

  kubectl -n shop get deployments -o custom-columns='NAME:.metadata.name,IMAGE:.spec.template.spec.containers[0].image'
  kubectl -n shop get pods,svc
  kubectl -n shop rollout status deployment/shop-user --timeout=10m
  kubectl -n shop rollout status deployment/shop-auth --timeout=10m
  kubectl -n shop rollout status deployment/shop-product --timeout=10m
  kubectl -n shop rollout status deployment/shop-cart --timeout=10m
  kubectl apply -f k8s/ingress/shop-ingress.yaml
  kubectl -n shop get ingress

If a deployment fails, check pod status/events/logs before rerunning Jenkins:

  kubectl -n shop get pods -o wide
  kubectl -n shop get events --sort-by=.lastTimestamp
  kubectl -n shop describe deployment shop-auth
  kubectl -n shop logs deployment/shop-auth --all-containers --tail=150
  bash scripts/troubleshooting/diagnose.sh shop

To roll back one service to its previous Helm revision, first inspect history:

  helm -n shop history shop-auth-service
  helm -n shop rollback shop-auth-service

The Helm release names are `shop-user-service`, `shop-auth-service`,
`shop-product-service`, and `shop-cart-service`.


6. EXPOSE THE INGRESS TO THE LAPTOP
-----------------------------------

For VirtualBox VM networking, first confirm the ingress controller is ready.
Port-forward the NGINX ingress service on VM2 and restrict access to the
host-only subnet in the firewall:

  kubectl -n ingress-nginx get pods,svc
  sudo ufw allow from 192.168.56.0/24 to any port 8080 proto tcp
  kubectl -n ingress-nginx port-forward --address 0.0.0.0 svc/ingress-nginx-controller 8080:80

Leave the port-forward command running. On the Windows laptop, open
PowerShell as Administrator and add the host mapping (replace the IP):

  Add-Content -Path "$env:WINDIR\System32\drivers\etc\hosts" -Value "192.168.56.102 shop.local"

Open the storefront from the laptop browser:

  http://shop.local:8080/

On Windows PowerShell, confirm the host-only address and port are reachable:

  Test-NetConnection 192.168.56.102 -Port 8080

The storefront includes grocery search, account sign-in/registration, and
shopping-cart controls. Test the product API directly from PowerShell:

  Invoke-RestMethod 'http://shop.local:8080/api/products?q=camera'

The Ingress routes /api/auth, /api/users, /api/products, and /api/cart to
the corresponding service. If it does not respond, check that VM2's
host-only IP is reachable, the firewall allows port 8080 from the host-only
subnet, ingress-nginx is running, and the port-forward command is active.

This is a local learning environment, not a production-ready public
deployment. Production needs TLS, durable data stores, secret management,
backups, monitoring/alerting, and a production-supported load balancer.


7. OPTIONAL PROMETHEUS AND GRAFANA DEPLOYMENT
---------------------------------------------

Prometheus collects service, JVM, and Kubernetes-object metrics and evaluates
alert rules. Grafana displays collected metrics in dashboards. The Helm chart also
installs Prometheus Operator, Alertmanager, and kube-state-metrics. This is
an optional Kubernetes deployment in the separate "monitoring" namespace.
It is not part of the four shop application deployments. Node exporter is
disabled in the laptop profile to save resources.

On this 16 GB laptop, stop VM1 first, keep at least 2 GB free in VM2 for
monitoring, and avoid Jenkins builds while it runs. The supplied profile
limits Prometheus retention to 12 hours and uses ephemeral storage. It does
not install centralized logs or distributed tracing and does not send alerts
to email/Slack/Teams.

First update the VM2 clone before creating any local configuration:

  cd ~/k8-lab
  git pull --ff-only origin srinath6132-minikube-microservices

Set a private Grafana password in a local override file outside the
repository. This generates a random 48-character hex password, prints it so
you can save it, and keeps it out of Git:

  mkdir -p "$HOME/.config/k8-lab"
  chmod 700 "$HOME/.config/k8-lab"
  GRAFANA_PASSWORD="$(openssl rand -hex 24)"
  printf 'grafana:\n  adminPassword: "%s"\n' "$GRAFANA_PASSWORD" > "$HOME/.config/k8-lab/monitoring-values.yaml"
  chmod 600 "$HOME/.config/k8-lab/monitoring-values.yaml"
  printf 'Save this Grafana password: %s\n' "$GRAFANA_PASSWORD"
  unset GRAFANA_PASSWORD

As the account that owns Minikube, install the chart and this project's
ServiceMonitor, alert rules, and Grafana dashboard:

  MONITORING_VALUES_OVERRIDE="$HOME/.config/k8-lab/monitoring-values.yaml" bash scripts/observability/install-laptop-monitoring.sh

The script uses Helm to install/update the kube-prometheus-stack release
named "monitoring" in namespace "monitoring". It waits for the Prometheus
Operator CRDs, then registers the shop ServiceMonitor and alert rules and
provisions the dashboard ConfigMap. It is safe to rerun to apply updates.
The shop services should already be deployed and ready before installing.

Wait for the monitoring pods and inspect the created resources:

  kubectl -n monitoring get pods,svc
  kubectl -n monitoring get servicemonitors,prometheusrules
  kubectl -n shop get pods,svc

Wait until the Grafana, Prometheus, operator, Alertmanager, and
kube-state-metrics pods are Ready. The ServiceMonitor scrapes the four shop
services at `/actuator/prometheus` every 30 seconds; its `release: monitoring`
label must match the Helm release name.

To access both UIs securely from Windows, open two terminals on VM2 and
leave these port-forwards running:

  kubectl -n monitoring port-forward --address 127.0.0.1 svc/monitoring-grafana 3000:80

  kubectl -n monitoring port-forward --address 127.0.0.1 svc/monitoring-kube-prometheus-prometheus 9090:9090

In Windows PowerShell, open one SSH tunnel to VM2 and leave it running:

  ssh -N -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 deploy@192.168.56.102

Open these addresses on Windows:

  Grafana:    http://localhost:3000
  Prometheus: http://localhost:9090

Sign into Grafana as `admin` using the password set in
`$HOME/.config/k8-lab/monitoring-values.yaml`. Keep this file and password
private. Reuse the same override path whenever you rerun the install script;
this lets you update the chart without storing the password in the repo.
Open Dashboards and select
"K8 Lab Shop Services". It shows HTTP request rate, p95 latency, JVM heap,
and container restart counts. In Prometheus, open Status > Targets and check
that the shop service endpoints are UP. In Graph, try:

  up{namespace="shop"}

The alert rules cover missing service scrapes, unavailable shop replicas,
repeated container restarts, and containers near their memory limits. View
their state at http://localhost:9090/alerts or in Grafana's Alerting area.
They are warning rules only; this lab does not configure external alert
notifications.

If targets are missing or DOWN, check that application pods are Ready, the
shop ServiceMonitor exists in namespace monitoring, the `release: monitoring`
label is present, and the shop Services expose port `http`. Useful checks:

  kubectl -n monitoring get servicemonitor shop-services -o yaml
  kubectl -n monitoring get prometheusrule shop-service-alerts -o yaml
  kubectl -n shop get svc --show-labels
  kubectl -n monitoring get events --sort-by=.lastTimestamp
  kubectl -n monitoring logs deployment/monitoring-kube-prometheus-operator --tail=100

To make `kubectl top` available for an additional quick resource check,
enable Minikube's metrics-server addon (separate from Prometheus):

  minikube addons enable metrics-server
  kubectl top nodes
  kubectl top pods -A

When finished, uninstall monitoring and remove its namespace to free VM2
resources. This deletes the Prometheus/Grafana data and dashboard:

  bash scripts/observability/remove-laptop-monitoring.sh

If the monitoring release is already absent, the cleanup script may report
that Helm cannot find it; in that case remove the leftover namespace with:

  kubectl delete namespace monitoring

Do not delete the `shop` namespace when cleaning up monitoring.


8. TROUBLESHOOTING AND APPLICATION CHECKS
-----------------------------------------

To check one service's actuator health endpoint from VM2, use a temporary
port-forward in another terminal (example: auth service):

  kubectl -n shop port-forward svc/shop-auth 18081:8080
  curl http://127.0.0.1:18081/actuator/health

Run the diagnostic script for pod details, events, current/previous logs,
and Helm release status:

  bash scripts/troubleshooting/diagnose.sh shop

Run a non-destructive storefront and grocery-catalog smoke test:

  bash scripts/smoke-test.sh http://127.0.0.1:8080

The smoke test should run on VM2 while the Ingress port-forward above is
active. Its `Host: shop.local` header selects the configured Ingress route.

First-response procedures are documented in runbooks/:

  runbooks/pod-startup-and-probes.md
  runbooks/helm-deployment-failure.md
  runbooks/image-pull-failure.md
  runbooks/ingress-and-service-unavailable.md
  runbooks/laptop-operations.md
  runbooks/jenkins-build-and-status.md

To stop the app and recover laptop resources, remove the optional monitoring
stack if installed, then scale down the four services:

  bash scripts/observability/remove-laptop-monitoring.sh
  kubectl -n shop scale deployment --all --replicas=0

To bring the services back, rerun the Jenkins orchestrator deployment or
scale them up:

  kubectl -n shop scale deployment --all --replicas=1

The deployment uses ephemeral/in-memory application data, so restarting
services loses demo users and cart contents.
